# RAG 三阶段架构：检索层 → 增强层 → 生成层

## 概述

ChatBI 的 RAG 架构严格遵循经典三阶段模型：**检索(Retrieve) → 增强(Augment) → 生成(Generate)**。
代码中 `UnifiedRAGExecutor` 类显式定义了这三个阶段方法（`retrieve()` → `augment()` → 生成由 LLMService 执行）。

本文档的核心目的：**明确每个知识组件（术语库、SQL示例库、自定义提示词、文档知识库、Schema）
在 RAG 三阶段中的精确位置**，解决答辩中"什么在检索层、什么在增强层、什么在生成层"的问题。

## 前端 RAG Phase 标注与后端三阶段的映射

前端有两套 RAG 阶段展示组件，它们的 Phase 标注与后端三阶段的对应关系如下：

### RagProcessIndicator（进度条）

| 进度条阶段 | Phase 标注 | 后端实际操作 |
|-----------|-----------|-------------|
| 🔍 RAG知识检索 | `R+A` | Pre-RAG(查询理解) + R(检索) + A(增强/Prompt构建) |
| 🧠 SQL生成 | `G` | G层：LLM基于增强后Prompt生成SQL |
| ⚡ SQL执行 | `G` | G层后处理：执行SQL返回数据 |
| 📊 图表生成 | `G` | G层输出：LLM生成图表配置 |
| 📈 数据分析 | `G` | G层：LLM生成分析报告 |
| 🔮 数据预测 | `G` | G层：LLM生成预测报告 |

### BaseAnswer 思考过程面板（6步推理链）

| 步骤 | Phase 标注 | 后端实际操作 |
|------|-----------|-------------|
| 步骤1: 🎯 查询理解 | `Pre-R` | Pre-RAG：意图检测 + 查询重写 + 指代消解 |
| 步骤2: 🔍 知识检索 | `Retrieve` | R层：术语库/SQL示例库/文档知识库检索 + 重排序 |
| 步骤3: 🔧 上下文增强 | `Augment` | A层：知识注入Prompt + 上下文压缩 + 可视化判定 |
| 步骤4: 🤖 大模型推理 | `Generate` | G层：LLM推理（SQL/文本/分析/预测） |
| 步骤5: 📊 结果输出 | `Generate` | G层后处理：SQL执行 + 图表渲染 |
| 步骤6: 📈 深度分析 | `Generate` | G层：内联分析/预测报告生成 |

### 检索层关键设计决策

1. **术语库和SQL示例库都在检索层**：它们通过向量检索（pgvector）和关键词匹配（ILIKE）
   从数据库中召回相关知识，这是典型的 Retrieval 操作。

2. **SQL示例库不是"增强层"**：虽然 SQL 示例最终会注入 Prompt，但它的获取过程
   是通过三通道混合检索（ILIKE + 分词模糊 + 向量语义），属于检索行为。
   注入 Prompt 的动作属于增强层。

3. **重排序属于检索层后处理**：RAGReranker 在检索结果上做质量优化，
   是检索管线的一部分，不是增强层。

### 增强层关键设计决策

1. **自定义提示词是纯增强层组件**：它通过关键词匹配（非向量检索）获取，
   直接注入 Prompt，不经过检索层的向量检索管线。

2. **Schema 是纯增强层组件**：运行时直接读取数据库元数据，不需要语义检索。

3. **术语和SQL示例跨越 R→A 两层**：检索层负责召回，增强层负责格式化和注入。
   答辩时可以说"术语库同时参与检索层和增强层"。

4. **上下文压缩是增强层的质量优化手段**：在注入 Prompt 之前，
   按 Token 预算裁剪各知识组件，确保不超出 LLM 上下文窗口。

## 答辩话术要点

### "SQL示例库在检索层还是增强层？"

SQL示例库**跨越检索层和增强层**：
- **检索层**：通过三通道混合检索（ILIKE子串匹配 + 分词级模糊匹配 + pgvector向量语义检索）
  从 `data_training` 表中召回与用户问题语义相似的 SQL 示例。这是典型的 Retrieval 操作。
- **增强层**：将检索到的 SQL 示例格式化为 XML 结构，经过上下文压缩（Token预算30%），
  注入到 Prompt 的 system message 中，作为 LLM 的 few-shot 参考。这是 Augmentation 操作。

### "自定义提示词在哪一层？"

自定义提示词是**纯增强层组件**：
- 它不经过向量检索，而是通过关键词匹配（`match_type='keyword'`）或 `always_inject` 标记获取。
- 直接注入 Prompt，属于规则型知识注入，不涉及语义检索。
- 这是 ChatBI 相比 SQLBot 新增的增强层能力。

### "术语库在哪一层？"

术语库**跨越检索层和增强层**，且是**唯一跨双轨道共享的知识源**：
- **检索层**：向量检索 + 关键词匹配，召回相关业务术语。
- **增强层**：SQL轨道注入完整字段（word + description + sql_mapping），
  文档轨道注入裁剪字段（word + description，过滤 sql_mapping）。
- **预处理层**：术语还参与查询重写阶段的同义词扩展（`post_expand_with_terminologies`）。

### "Schema在哪一层？"

Schema是**纯增强层组件**：
- 运行时直接读取数据库元数据（表名、字段名、类型、外键、注释），不经过向量检索。
- 直接注入 Prompt，占 Token 预算的 45%（SQL轨道最高优先级）。
